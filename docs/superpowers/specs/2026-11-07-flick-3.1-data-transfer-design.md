# Flick 3.1 — 파일 내보내기/가져오기 설계

작성일: 2026-11-07 / 기준: iOS main `05eb171`(스토어 3.0.1), 안드로이드 `android-spike` 브랜치(미출시)

## 왜 하는가

안드로이드 버전이 나오면 iPhone에서 옮겨 갈 사용자가 생긴다. Flick은 서버도 계정도 없어서 지금은 기기 밖으로 데이터를 꺼낼 방법이 없다. 3.1에서 Pro 대신 파일 기반 이전을 먼저 낸다. 리뷰의 백업 요청 2건도 함께 해결된다.

## 3.1 범위

1. 파일 내보내기/가져오기 (이 문서의 본론)
2. 버그 수정: 빈 메모 전송 차단, 입력창 확장 시 목록 가림 확인 및 수정
3. 스토어 노트 정정: 링크 여는 방법

버전은 3.1.0, 무료 업데이트.

## 목표

- iOS와 안드로이드가 같은 파일을 양방향으로 읽고 쓴다.
- 같은 파일을 여러 번 가져와도 항목이 늘어나지 않는다.
- 서버, 계정, 네트워크가 필요 없다.

## 하지 않는 것

- Flick Pro: 3.1에 넣지 않는다. 시기는 미정이며 다음 버전 이후로 넘긴다.
- 날짜 지정: 논의 후 제외했다.
- 미루기: 제외했다. 날짜 간 드래그로 대신할 수 있다. 단, 오늘 항목이 없으면 오늘 섹션이 없어 끌어다 놓을 수 없는 한계는 그대로 둔다.
- 자동 백업, iCloud 동기화, 실시간 동기화
- 설정 이전: 테마, 화면 스타일, 고정 바 접힘, 최초 실행 여부는 기기별 값으로 두고 파일에 넣지 않는다.
- 파일 암호화

## 실패로 보는 경우

- 가져오기 때문에 기존 항목이 사라지는 경우 (아래 안내 항목 제거는 예외)
- 잘못된 파일을 가져와서 데이터가 일부만 바뀌는 경우
- 고정 항목이나 아카이브가 옮겨지지 않는 경우

## 검토한 방식

| 방식 | 장단점 | 결정 |
|---|---|---|
| JSON 파일 공유 | 서버가 필요 없고 메신저·메일·파일 앱으로 바로 옮길 수 있다. 사용자가 파일을 직접 다뤄야 한다. | **채택** |
| 서버 동기화 | 가장 편하지만 서버 없는 앱 원칙에 어긋나고 계정이 필요하다. | 제외 |
| 텍스트 복사 또는 QR | 파일이 필요 없지만 메모가 많으면 쓸 수 없다. | 제외 |

가져오기 방식은 전체 교체와 합치기를 비교해 **합치기**로 정했다. 기기에 있던 데이터를 잃지 않기 때문이다.

## 사용자 흐름

두 앱의 설정 화면에 같은 두 줄을 추가한다.

**데이터 내보내기**
1. 항목이 하나도 없으면 "내보낼 항목이 없어요"를 보여주고 끝낸다.
2. `flick-backup-YYYY-MM-DD.json`을 만들고 공유 화면을 연다.
3. 파일은 암호화되지 않으므로 공유 전에 그 사실을 안내한다.

**데이터 가져오기**
1. 파일 선택 화면을 연다.
2. 파일을 끝까지 읽고 검증한다. 실패하면 안내만 하고 기존 데이터는 건드리지 않는다.
3. 합치기 결과를 미리 계산해 "새 항목 N개를 추가할게요. 이미 있는 M개는 건너뛰어요."를 확인 창으로 보여준다.
4. 확인하면 합친 뒤 한 번에 저장하고, 메인·아카이브·고정 바·위젯을 갱신한다.
5. 새 항목이 0개이면 "이미 모두 들어 있어요"만 보여주고 저장하지 않는다.

오류 문구는 두 가지로 구분한다.
- 형식이 틀린 파일: "Flick 데이터 파일이 아니에요"
- 앱보다 새 버전의 파일: "앱을 업데이트한 뒤 다시 가져와 주세요"

## 파일 형식

```json
{
  "format": "flick-backup",
  "version": 1,
  "exportedAt": "2026-11-07T09:30:00Z",
  "source": { "platform": "ios", "appVersion": "3.1.0" },
  "todos": [
    { "date": "2026.11.07", "items": [{ "date": "2026.11.07", "todo": "보고서", "isImportant": true }] }
  ],
  "pinned": [
    { "date": "2026.11.01", "todo": "고정 메모", "isImportant": false }
  ],
  "archive": [
    { "date": "2026.11.06", "items": [{ "date": "2026.11.02", "todo": "완료한 일", "isImportant": false }] }
  ]
}
```

- 날짜는 `yyyy.MM.dd` 문자열이다. 두 앱의 현재 형식과 같다.
- `todos`는 섹션 순서(날짜 오름차순)와 섹션 안 순서를 그대로 담는다.
- `pinned`는 현재 순서(최근 고정이 앞)를 담는다. 고정 여부는 이 배열로 표현하므로 `isPinned`는 넣지 않는다.
- `archive`의 바깥 `date`는 완료한 날짜, 항목의 `date`는 원래 작성 날짜다. 섹션은 최신순이다.
- 안드로이드 내부 `id`는 파일에 넣지 않는다. 가져올 때 안드로이드가 새로 만든다.
- 읽는 쪽은 모르는 필드를 무시한다. `version`이 지원 범위보다 크면 거절한다.

## 합치기 규칙

**같은 항목의 기준**
- 할 일과 고정: `날짜 + 내용`이 정확히 같으면 같은 항목이다. 일반 목록과 고정 목록은 한 묶음으로 비교한다.
- 아카이브: `완료 날짜 + 작성 날짜 + 내용`이 같으면 같은 항목이다.
- 일반 목록과 아카이브는 따로 비교한다. 한 기기에서만 완료한 일은 양쪽에 모두 남을 수 있다.

**개수 처리**

같은 기준의 항목이 파일에 a개, 기기에 b개 있으면 `max(0, a - b)`개만 추가한다. 같은 날 같은 메모를 두 번 적은 경우를 보존하면서, 같은 파일을 다시 가져와도 늘어나지 않게 하기 위해서다.

**상태 충돌**

이미 있는 항목은 기기 쪽 상태를 유지한다. 중요 표시와 고정 여부를 파일 값으로 바꾸지 않는다.

**위치**
- 할 일: 날짜 오름차순을 지켜 해당 날짜 섹션 끝에 붙인다. 섹션이 없으면 날짜순 위치에 새로 만든다.
- 고정: 기존 고정 목록 뒤에 파일 순서대로 붙인다. 가져온 항목이 기존 고정을 밀어내지 않게 하기 위해서다.
- 아카이브: 완료 날짜 내림차순을 지켜 해당 섹션 끝에 붙인다. 기존 `appendToArchive`는 새 날짜를 무조건 맨 앞에 넣으므로 그대로 쓰면 안 된다.

**안내 항목**

새로 설치한 앱에는 안내 할 일 3개가 들어 있다. 세 문구가 모두 같은 날짜로, 수정 없이 일반 목록에 있으면 "안내 세트"로 본다. 하나라도 지웠거나 수정했으면 사용자가 손댄 것으로 보고 일반 항목으로 취급한다.

- 파일 쪽 안내 세트는 가져오지 않는다. N과 M 어디에도 세지 않는다.
- 기기 쪽 안내 세트는 실제로 추가되는 항목이 1개 이상일 때만 지운다.
- 이렇게 하면 같은 파일을 다시 가져와도 N은 0이고, 파일에 안내 세트만 있으면 아무것도 바뀌지 않는다.

세 문구는 두 앱이 같다.
- 왼쪽으로 밀어서 완료 상태로 만들어 보세요.
- 두 번 탭해서 중요 표시를 해 보세요.
- 한 번 클릭해서 메모를 삭제하거나 수정할 수 있어요.

## 안정성

- 검증과 합치기는 메모리에서 끝낸 뒤 마지막에 한 번만 저장한다. 중간 실패가 기존 데이터에 남지 않게 하기 위해서다.
- 항목 수나 파일 크기에 인위적인 제한은 두지 않는다.

기존 iOS 데이터에는 형식에 맞지 않는 값이 있을 수 있다. 내보낼 때 정리해서 파일에는 항상 올바른 값만 담는다.

| 기존 데이터 | 내보낼 때 처리 | 이유 |
|---|---|---|
| 내용이 비었거나 공백·줄바꿈만 있는 메모 | 제외 | 전송과 수정 화면의 빈 입력 검사가 부족해 생긴 값이고, 옮길 내용이 없다 |
| `yyyy.MM.dd HH:mm` 같은 옛 날짜 (1.0x 시절) | 앞 10자로 바꾼다 | 내용을 보존하면서 형식을 맞춘다 |
| 비어 있거나 읽을 수 없는 날짜 | 섹션 날짜, 그것도 없으면 내보내는 날짜로 채운다 | 항목을 잃지 않기 위해서다 |

가져올 때는 엄격하게 검증한다. `date`가 `yyyy.MM.dd`가 아니거나 `todo`가 공백뿐인 항목이 하나라도 있으면 파일 전체를 "Flick 데이터 파일이 아니에요"로 거절한다. 일부만 가져오면 사용자가 알아채기 어렵기 때문이다. 정상적으로 내보낸 파일은 항상 이 검증을 통과한다.

## iOS 구현 방향

- 데이터 로직은 `TDT/TDT/Data/TodoStore.swift`에 내보내기와 합치기를 두고, UI 없이 `TDT/Tests/TodoStoreTests.swift`로 검증한다.
- 파일 형식 모델은 Codable로 새로 만든다. 저장소의 PropertyList 형식은 바꾸지 않는다.
- 설정 화면(`SettingViewController.swift`)에 새 섹션을 추가한다. 내보내기는 `UIActivityViewController`, 가져오기는 `UIDocumentPickerViewController`를 쓴다.
- 가져온 뒤 `WidgetDataManager.shared.updateData()`를 호출한다.
- 메인과 아카이브는 `viewWillAppear`에서 다시 읽는다. 설정 화면이 떠 있는 동안 이미 보이는 화면이 있다면 별도 갱신이 필요한지 구현 시 확인한다.
- `MARKETING_VERSION`은 앱과 위젯 대상 모두 3.1.0으로 올린다.

## 안드로이드 구현 방향

- `TodoStore.kt`에 같은 내보내기와 합치기를 구현하고 `TodoStoreTest.kt`로 검증한다.
- 설정 화면에 같은 두 줄을 추가하고 시스템 파일 공유와 파일 선택을 쓴다.
- 안드로이드는 1.0부터 두 기능을 포함한다.
- 두 플랫폼이 같은 샘플 JSON을 테스트에 사용해 형식이 어긋나지 않게 한다. 샘플에는 한글, 줄바꿈, 고정, 아카이브, 같은 날 중복 메모를 넣는다.

## 버그 수정

**빈 메모 전송 차단**

공백과 줄바꿈만 있는 입력은 저장하지 않는다. 내용이 있는 메모는 입력한 그대로 저장한다.

- iOS 메인 입력창: 전송 버튼을 빈 입력일 때처럼 비활성 색으로 두고 전송을 막는다.
- iOS 수정 화면: 지금은 검사가 없어 내용을 비우면 빈 메모로 저장된다. 할 일과 고정 항목 모두 같은 입력이면 저장하지 않는다.
- 안드로이드: 전송과 수정 모두 이미 `isNotBlank`로 막고 있어 변경이 없다.

**입력창 확장 시 목록 가림**

입력창은 최대 120pt까지 커지지만 목록 하단 여백은 키보드 높이만 반영한다. 실기기에서 맨 아래 항목이 가려지는지 먼저 확인한다. 재현되면 늘어난 높이만큼 하단 여백을 더한다.

## 출시 순서

1. iOS 3.1을 먼저 제출한다. 안드로이드 왕복 확인을 기다리지 않는다.
2. 안드로이드 1.0을 가져오기와 내보내기를 포함해 구현한다.
3. 안드로이드 출시 전에 iOS와 안드로이드 사이 왕복을 실기기로 확인한다.
4. 안드로이드 1.0을 출시한다.

iOS를 먼저 내면 사용자가 안드로이드 출시 전에 파일을 받아둘 수 있다. 대신 version 1 형식이 먼저 굳으므로, iOS 작업에서 만든 샘플 JSON을 형식의 기준으로 삼는다. 안드로이드는 이 샘플을 그대로 읽어야 하고, 안드로이드 작업 중 형식 문제가 나오면 version 1 파일을 계속 읽을 수 있게 고친다.

iOS 작업은 `main`에서 갈라진 `feature/3.1`에서 진행하므로 `android-spike` 병합을 기다리지 않는다. 샘플 JSON은 `main`에 두고, `android-spike`를 합칠 때 안드로이드 테스트에 연결한다.

## 확인 기준

iOS 3.1 제출 전:

- iPhone에서 내보낸 파일을 다른 iPhone 또는 초기화한 앱으로 가져왔을 때 할 일·고정·아카이브가 모두 옮겨진다.
- 샘플 JSON을 iOS가 정확히 읽고, iOS 내보내기 결과가 같은 구조로 나온다.
- 같은 파일을 두 번 가져와도 두 번째는 추가되는 항목이 없다.
- 잘못된 파일을 가져와도 기존 데이터가 그대로다.
- 새 기기에서 가져오면 안내 세트가 양쪽 어디서도 남지 않는다.
- 빈 메모나 옛 날짜 형식이 있는 iOS 데이터도 내보낸 파일이 두 앱에서 정상적으로 읽힌다.
- 가져온 뒤 위젯에 반영된다.
- 기존 테스트가 모두 통과한다.

안드로이드 1.0 출시 전:

- iOS에서 내보낸 파일을 안드로이드에서, 안드로이드에서 내보낸 파일을 iOS에서 가져왔을 때 할 일·고정·아카이브가 모두 옮겨진다.
